# Product Specification: CUE（仮）

- Status: Draft v0.1
- Date: 2026-08-18
- Platform: スマートフォン向けWebアプリ
- Primary users: 大学の新入生、部活・サークルの新歓担当者

## 1. ビジョン

新歓で「自分から知らない集団に入っていく」ことを必須にせず、興味に合う団体から安全なきっかけが届く状態を作る。

## 2. 一文での説明

新入生が興味と参加条件を登録すると、相性の合う部活・サークルから、届いた理由付きの新歓案内を受け取れる許可制オファーサービス。

## 3. 問題

### 新入生側

- 新歓情報がSNS、ビラ、ブース、口コミに分散している
- 興味があっても、自分から連絡・応募する最初の一歩が重い
- 入学直後は、自分に合う活動頻度や雰囲気を判断しにくい
- 活動内容だけでなく、曜日、費用、本気度、初心者対応などの比較が難しい
- 参加申請が「入会意思の表明」のように感じられ、気軽な見学になりにくい

### 団体側

- ブースやSNSまで来てくれる顕在層に接点が偏る
- 団体名や競技名を知らない潜在層へ届きにくい
- 大量告知はできても、誰に適合する案内かを説明できない
- 閲覧から参加までのどこで離脱したか分からない

## 4. 中核仮説

新入生が事前に関心領域と受信条件を指定し、適合する団体から低圧な案内が届くようにすれば、自発応募だけの場合よりも「検討する団体数」と「新歓イベント参加率」が上がる。

この仮説は未検証であり、ユーザー調査で確認する。

## 5. 差別化

既存の主要サービスは、サークル検索、絞り込み、掲示、入会申請、イベント参加を中心にしている。CUEは、学生が検索を始める前に、受信を許可した条件へ団体側から案内が届く点を核にする。

差別化は「スカウト」だけではない。次の4点を一体化する。

1. 許可制: 学生がカテゴリと受信量を決める
2. 匿名性: 承諾前に個人情報を団体へ公開しない
3. 説明可能性: 届いた理由を示す
4. 低圧な返答: 承諾・拒否の二択にしない

## 6. Jobs to Be Done

### 新入生

大学生活を始めたばかりで自分に合う居場所が分からないとき、個別に検索・連絡しなくても、興味や生活条件に合う選択肢を知り、心理的負担を抑えて見学の一歩を踏み出したい。

### 団体

新歓で新しい参加者を集めたいとき、すでに自団体を知っている人だけでなく、活動と相性の良い潜在層へ、迷惑にならない形で案内を届けたい。

## 7. コアフロー

### 新入生

1. サービス説明と受信同意
2. 興味パスポート登録
3. 受信カテゴリ・上限設定
4. オファー受信
5. マッチ理由、日時、費用、雰囲気を確認
6. 「行ってみたい／あとで考える／今回は見送る」
7. 行ってみたい場合のみ、参加詳細へ進む

### 団体

1. 団体プロフィール確認
2. 新歓イベント作成
3. 対象とする興味・参加条件を設定
4. マッチ人数と送信条件をプレビュー
5. オファー送信
6. 閲覧・関心・参加予定を確認

## 8. MVP要件

### P0: 審査デモに必須

#### 新入生側

- 初回オンボーディング
- 興味カテゴリの複数選択
- 活動目的、本気度、曜日、頻度、予算、経験の登録
- オファー受信箱
- オファー詳細
- マッチ理由の表示
- 3段階の返答
- 受信停止・通報への導線

#### 団体側

- 団体プロフィール表示
- イベント・オファー作成
- 対象条件設定
- マッチ対象人数のプレビュー
- 送信確認
- 簡易ファネル表示

#### システム

- 説明可能なルールベースマッチング
- 架空の学生・団体・イベントデータ
- 役割切替による一台完結デモ
- スマートフォン表示
- リロード後もデモ状態を保てるローカル保存

### P1: P0完成後

- お気に入り・比較
- カレンダー追加
- 同じイベントに関心を示した新入生数の匿名表示
- 団体認証・管理者審査の画面
- マッチ条件の改善フィードバック

### MVPの対象外

- 学生間の直接マッチング
- 承諾前の個別チャット
- 決済
- 正確な現在地・常時位置情報
- 実在学生データ
- AIによる人格評価
- 本番用プッシュ通知

## 9. 成功指標

### North Star Metric

適合オファーから新歓イベント参加意向に進んだ割合。

### 補助指標

- 興味パスポート完了率
- オファー開封率
- 「行ってみたい」率
- 「あとで考える」率
- 見送り理由
- 通報・ミュート率
- 団体別の送信集中度
- マッチ理由の納得度

オファー送信数そのものを成功指標にしない。

## 10. 検証すべき仮説

1. 自分から応募するより、関連性の高い招待を受け取る方が参加しやすいか
2. 「オファー」という言葉は歓迎されるか、圧迫感を生むか
3. どのプロフィール項目なら抵抗なく登録できるか
4. 団体が学生個人を見られなくても、条件指定型の案内に価値を感じるか
5. 「あとで考える」が参加への心理的負担を下げるか
6. 何件までなら通知を迷惑に感じないか

## 11.1 Phase 1実装上の確定事項（2026-08-22デモ・達成済み）

- 2026年8月22日（土）までにデモ版を完成させる
- ゼミメンバーが各自の成果物を持ち寄る
- Vite + React + TypeScriptを使う
- localStorageと架空データで両ロールの連動を再現する
- 認証・本番DB・実通知は作らない（Phase 1限定の制約。D026により解除）
- GitHub Pagesで共有可能なURLを用意する方針とする

## 11.2 Phase 2の確定事項（2026-08-24承認・D026〜D031）

- 大学メール（`stu.kobe-u.ac.jp`・メールOTP）によるアカウント登録・ログイン。パスワードとMagic Linkは使わない
- 新入生と団体担当者の権限分離。一人が複数の役割・複数団体への所属を持てる
- 団体は共有アカウントにせず、複数担当者が所属する組織として管理する（owner / admin / member、pending / verified / suspended）
- localStorageからサーバーデータ（Supabase PostgreSQL + RLS）へ移行する
- オファー到着時に登録メールへ通知する（Resend候補・Task 010）
- 団体側には学生のメール・氏名・学籍番号を表示しない
- Task 008（認証・権限基盤）/ 009（サーバーデータ移行）/ 010（メール通知）/ 011（運用・セキュリティQA）の4PRへ分割し、PRのbaseは`develop`とする（`main`と公開デモは凍結）
- 詳細仕様は `docs/auth_and_authorization.md` を正本とする
