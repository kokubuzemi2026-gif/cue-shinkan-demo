# Matching and Safety Design

## 1. 設計原則

CUEのマッチングは、団体が学生個人を検索して選別する仕組みではありません。

1. 学生が受信を許可した条件を登録する
2. 団体がイベントと対象条件を登録する
3. システムが適合度を計算する
4. 団体には対象者の個人一覧ではなく、マッチ人数を示す
5. 案内は条件を満たす学生へ個別に届く
6. 学生が関心を示した後にだけ、次の接点を開く

この方式により、逆オファーの価値を残しながら、外見・属性による選別と無差別勧誘を抑える。

## 2. 興味パスポート

### MVPで登録する項目

| 項目 | 例 | 団体への表示 | 用途 |
|---|---|---:|---|
| 興味カテゴリ | アウトドア、音楽、スポーツ | 集計のみ | 中核マッチ |
| 活動目的 | 友達、挑戦、運動、創作 | 集計のみ | 文化適合 |
| 活動スタイル | ゆるく、ほどほど、本格的 | 集計のみ | 本気度適合 |
| 希望頻度 | 月1、週1、週2以上 | 集計のみ | 負担適合 |
| 参加可能曜日 | 平日夜、土日など | 集計のみ | 日程適合 |
| 月額予算帯 | 〜1,000円、〜5,000円など | 集計のみ | 費用適合 |
| 経験 | 未経験、少し、経験者 | 集計のみ | 初心者対応適合 |
| キャンパス | 活動可能エリア | 集計のみ | 移動適合 |
| 受信設定 | カテゴリ、上限、停止 | 非表示 | 利用者制御 |

### MVPで収集しない項目

- 氏名
- 顔写真
- 学籍番号
- 性別
- 国籍・人種・宗教
- 病歴・障害
- 電話番号
- 自由記述の自己PR
- 正確な住所・位置情報

## 3. オファーキャンペーン

団体は次を登録する。

- 団体名・認証状態
- イベント名
- 活動内容
- 日時・場所
- 参加費
- 初心者対応
- 活動の本気度
- 対象としたい興味カテゴリ
- 対象としたい活動目的
- 必須の参加可能条件
- 参加定員
- 申込期限
- 「なぜこの人たちに届けたいか」の短い説明

## 4. マッチング方式

### 4.1 必須条件

次のいずれかを満たさない場合は配信対象外とする。

- 学生がオファー受信を有効にしている
- 学生が対象カテゴリの受信を許可している
- 対象大学・キャンパスが一致している
- イベント日時が明確に不可能ではない
- 学生側の受信上限を超えていない
- 団体が送信上限・安全要件を満たしている

### 4.2 適合度

初期案は100点満点のルールベースとする。

| 要素 | 配点 |
|---|---:|
| 興味カテゴリ | 35 |
| 活動目的・雰囲気 | 20 |
| 活動スタイル・本気度 | 15 |
| 曜日・時間 | 15 |
| 経験と初心者対応 | 10 |
| 費用 | 5 |
| 合計 | 100 |

初期配信閾値は65点を仮置きする。数値はユーザー検証後に変更する。

### 4.3 学生への説明

点数だけを見せず、次のような理由を最大3件表示する。

- 「アウトドアに興味がある」
- 「土日に参加しやすい」
- 「未経験歓迎の活動」

重要な不一致がある場合は隠さない。

- 「活動費は希望予算より高めです」
- 「活動頻度は希望より多めです」

## 5. オファー量の制御

プロトタイプでは以下を仮置きする。

- 学生: 1週間に受け取る上限を1〜5件から選択
- 団体: 1週間に作成できる有効キャンペーンは3件まで
- 同一イベントの再送は禁止
- 見送り後の個別追跡は禁止
- 通報率が閾値を超えた団体は送信停止表示

数値は固定仕様ではなく検証対象とする。

## 6. 低圧な返答設計

### 行ってみたい

参加方法と団体の公式連絡先を表示する。これは入会確約ではないことを明示する。

### あとで考える

受信箱に保留し、期限前に最大1回だけリマインドする。

### 今回は見送る

団体に個人単位の拒否情報を伝えない。任意で見送り理由を選べる。

## 7. リスクと対策

| リスク | 起こること | MVPでの対策 |
|---|---|---|
| スパム化 | 大量の勧誘が届く | 学生上限、団体上限、再送禁止 |
| 属性差別 | 特定属性だけが選ばれる | 個人一覧非公開、人口統計属性を収集しない |
| 個人特定 | タグの組合せから推測される | 団体には集計人数のみ表示、少人数条件を制限 |
| 断りづらさ | 招待が圧力になる | 保留、ワンタップ見送り、拒否非通知 |
| 偽団体・危険な勧誘 | 不適切なイベント | 認証表示、通報、送信停止のUI |
| 人気団体への集中 | 一部だけが露出を独占 | オファー量制限、学生側の多様性設計を検討 |
| ブラックボックス | なぜ届いたか分からない | ルールベース、理由・不一致を表示 |
| 情報の陳腐化 | 日時や費用が古い | 有効期限、更新日、期限切れ表示 |

## 8. 実装上の安全要件

- 架空データのみでデモする
- シークレットをクライアントへ埋め込まない
- 権限の異なる学生画面と団体画面を明確に分ける
- 将来DBを使う場合も、団体へ学生プロフィールの直接クエリ権限を与えない
- ログにプロフィール内容を不用意に出さない
- エラー時に個人データを画面表示しない

## 9. 受入条件

- 団体側から学生個人の氏名・顔・一覧が見えない
- 学生が受信カテゴリと上限を制御できる
- 全オファーに最低1件のマッチ理由がある
- 学生が保留・見送りできる
- 団体の送信上限が画面上で理解できる
- 通報・受信停止への導線がある
